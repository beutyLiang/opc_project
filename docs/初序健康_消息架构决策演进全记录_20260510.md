## 三、每个版本的详细决策过程

---

### v0.0 · 个人微信方案（5/7，秒杀）

**方案内容**：用个人微信号挂 AI 客服，通过 wx4py/itchat 等工具对接

**提出原因**：项目初期，最直觉的做法——用户加个人微信，AI 自动回复

**秒杀原因**：
- 微信官方严打第三方协议，随时封号
- 封号 = 丢失全部客户关系，不可逆
- 无法通过任何合规审查

**决策结论**：❌ 个人微信做 AI 客服 = 定时炸弹，直接排除

---

### v0.5 · 企业微信 · 外部联系人 + Dify Agent（5/8 上午）

**方案内容**：
- 用企业微信的「外部联系人」模式（用户扫渠道活码加企微好友）
- 后端用 Dify 做 Agent 编排
- 参考了特步等品牌的做法（用户在主聊天列表看到企微客服）

**选择外部联系人模式的原因**：
- 用户体验最好：出现在微信主聊天列表，不在"服务号"角落
- 支持渠道活码：扫码加好友时自动打标签，追踪用户来源（OPC 归属）
- 支持欢迎语：用户加好友后自动发测评卡片
- 有成熟案例：特步、瑞幸等大品牌验证过

**Dify 被替换的原因**（同日下午决策）：
- 我们的业务逻辑中，70% 的功能（记忆管理、定时推送、产品推荐、订单归因）需要自定义 Tool Calling
- Dify 的可视化编排在简单问答场景好用，但复杂业务逻辑下反而限制灵活性
- 自建 LangChain Agent 可以完全掌控 Prompt、Tool、Memory 的组合方式

**决策结论**：✅ 外部联系人模式确认 / ❌ Dify → LangChain

---

### v0.8 · 外部联系人 + LangChain + SCRM 过渡（5/8 下午）

**新发现的问题**：

在深入研究企微 API 文档后，我们发现了一个关键限制：

> **外部联系人模式下，「自动回复用户消息」需要「会话存档」功能。**  
> 会话存档的开通条件：企业微信认证 + ISV（独立软件开发商）资质，或者接入第三方 SCRM。

也就是说，如果我们只有企微基础能力：
- ✅ 用户扫码加好友 → 可以
- ✅ 发欢迎语 → 可以（10分钟内一次）
- ✅ 用户主动发消息 → 我们收得到回调
- ❌ **AI 自动回复用户消息** → 需要 SCRM 或 ISV 权限
- ❌ **主动给用户推送消息** → 需要「企业群发」API，每天每客户限 1 条

**SCRM 过渡方案的设计**：
- 接入第三方 SCRM（如微盛、微伴）作为消息中间层
- SCRM 拦截用户消息 → 转发给我们的 LangChain Agent → Agent 生成回复 → SCRM 代发
- 主动推送用「企业群发」API，每天每客户 1 条

**这个方案的隐忧**（当时已识别但暂时接受）：
1. 依赖第三方 SCRM，增加了一个不可控环节
2. 企业群发每天 1 条的限制太严格，影响业务（疗程提醒、节气推送等会互相挤占名额）
3. SCRM 的稳定性和数据安全无法保证

### v1.1 · API 修正（5/9 审核后）

**审核发现的问题**：

子默2号（审核 Agent）在审核技术说明书时发现：

> 代码中使用 `POST /cgi-bin/message/send` 发送消息给外部联系人用户，但这个 API 只能发给**企业内部员工**，不能发给外部客户。

**这意味着**：之前写的所有"用企微 API 发消息"的代码，在外部联系人场景下根本**跑不通**。

**修正措施**：
- 所有被动回复 → 改为通过 SCRM 代发
- 所有主动推送 → 改为通过「企业群发」API
- 技术说明书中标注了 v1.1 修正说明

**这次修正让我们意识到**：外部联系人 + SCRM 的方案，在消息发送层面**完全依赖第三方**，不是一个健康的架构。

### v1.2 · kf_account 通道切换（5/10 凌晨）

**转折点**：一场关于"ISV 代开发到底能不能主动推送"的深度调研

Zoey 提出疑问：ISV 代开发到底能不能针对沉默用户主动推送消息？

经过调研，结论是：
- ISV 代开发**可以**实现自动回复和主动推送
- 但需要通过微信官方的 ISV 审核，流程复杂、周期长
- 而且 ISV 权限下仍受「企业群发」1 条/天的限制

**这时 Zoey 追问了一个关键问题**：

> "这样就没法形成客服智能体服务全流程了。人工客服只有一个窗口，而智能体为了主动推送，还要做公众号、短信、小程序，用户会觉得非常杂乱。这个初序健康智能体到底还能做吗？"

**这个问题直接推动了架构方向的根本性转变。**

随后的讨论中，我们重新审视了微信客服（kf_account）通道：

| 对比项 | 外部联系人 + SCRM | kf_account |
|--------|:---:|:---:|
| 自动回复 | 需要 SCRM/ISV | ✅ 原生支持 |
| 主动推送 | 企业群发 1条/天 | ✅ 48h 内无限制 |
| 第三方依赖 | 必须有 SCRM | ❌ 无需任何第三方 |
| ISV 资质 | 需要 | ❌ 不需要 |
| 用户体验 | 主聊天列表 | 客服会话（稍弱） |
| 开通难度 | 企微认证 + SCRM | 企微认证即可 |

**kf_account 的核心优势**：
- `kf/send_msg` API 可以在 48h 窗口内**无限次**主动发消息给用户
- 不需要 ISV 资质，不需要 SCRM，完全原生
- 消息回调直连 FastAPI，无中间层

**决策**：废弃外部联系人 + SCRM 方案，全面切换到 kf_account

### v1.3 · 混合架构定稿（5/10 凌晨，当前版本）

**v1.2 遗留的最后一个问题**：

> kf_account 的 48h 窗口是"用户最后一次发消息"起算的。如果用户超过 48h 没有回复，API 会报错 45015，**无法再主动发消息**。

**Zoey 提出的解决思路**：

> "超过 48h 客户不回复，我用 RPA 的方式，模拟人类在客服工作台发一条消息，相当于一个激活。这样用户回复后，又是一个新的 48h 窗口，AI 客服就可以继续服务了。"

**讨论中澄清的几个关键概念**：

1. **48h 内的用户**：kf/send_msg 全自动，没有任何问题
2. **超过 48h 的沉默用户**：API 发不了，但人工客服在工作台页面上仍可手动发送
3. **超过 7 天的沉默用户**：即使人工在工作台上发消息，对方也收不到

**基于这些规则，我们设计了 RPA 激活策略**：

```
用户沉默 > 48h
    │
    ├── D+1（沉默第1天）：RPA 发激活消息 #1
    │     "小安这边关心一下你，这几天感觉怎么样呀？"
    │
    ├── D+4（沉默第4天）：RPA 发激活消息 #2
    │     "好久没聊了，最近有没有按时吃药呢？"
    │
    ├── D+10（沉默第10天）：RPA 发激活消息 #3（最后一次）
    │     "小安一直在这里，有需要随时找我哦~"
    │
    └── D+10 后：停止推送，标记为「休眠用户」

任何时刻用户回复 → 48h 窗口重置 → AI 立刻全自动接管
```

**v1.3 最终架构**：

```
┌─────────────────────────────────────────────────────┐
│                  v1.3 混合架构                        │
│                                                       │
│  用户 ←→ 企微 kf_account ←→ FastAPI 网关 ←→ Agent   │
│           │                                           │
│           ├─ 活跃用户（<48h）                         │
│           │   └─ kf/send_msg 全自动（AI 对话+推送）   │
│           │                                           │
│           └─ 沉默用户（>48h）                         │
│               └─ RPA 在客服工作台发激活消息            │
│                   └─ 用户回复 → 窗口重置 → AI 接管    │
└─────────────────────────────────────────────────────┘
```

### v1.4 · 框架层切换：LangChain -> LangGraph (5/10 晚)

**方案内容**：将核心大模型控制中枢由传统的 LangChain 线性 Agent 替换为具备状态流转能力的 **LangGraph**。

**提出原因**：
- 传统 LangChain 存在严重的“黑盒化”问题，在高度定制化的医疗场景中调试成本过高。
- 初序业务存在长周期问诊和复杂的人机协同（如 48 小时唤醒、人工介入审核），线性结构难以胜任。
- LangGraph 的状态机（State Machine）机制能完美解决用户打断、流程回退等业务痛点。

**决策结论**：✅ 彻底废弃传统 LangChain 调度，全面采用 LangGraph 作为 Agent 底层框架。

## 六、当前 v1.4 架构的核心代码逻辑

### 统一推送入口：`send_proactive_message`

```python
ACTIVATION_MESSAGES = [
    "小安这边关心一下你，这几天感觉怎么样呀？",
    "好久没聊了，最近有没有按时吃药呢？",
    "小安一直在这里，有需要随时找我哦~"
]

async def send_proactive_message(user_id: str, content: str) -> dict:
    """主动推送入口——自动判断用户状态选择通道，返回三态结果"""
    user = await db.fetchrow("SELECT * FROM users WHERE user_id = :uid", {"uid": user_id})
    silent_hours = (datetime.now() - user["last_message_at"]).total_seconds() / 3600
    
    if silent_hours < 48:
        # 活跃用户：kf API 直接发，全自动
        resp = requests.post(f".../kf/send_msg?access_token={token}", json={
            "touser": user_id, "open_kfid": KF_ACCOUNT_ID,
            "msgtype": "text", "text": {"content": content}
        })
        if resp.json().get("errcode") == 0:
            return {"status": "sent", "channel": "kf"}
        else:
            # kf 失败是系统错误，需告警，不走 RPA
            return {"status": "failed", "reason": "kf_api_error",
                    "errcode": resp.json().get("errcode")}
    
    # 沉默用户（> 48h）：走 RPA 激活
    if user["status"] == "dormant":
        return {"status": "failed", "reason": "user_dormant"}
    
    if user["activation_count"] < 3:
        activation_msg = ACTIVATION_MESSAGES[user["activation_count"]]
        await add_to_rpa_queue(user_id, activation_msg)  # 写入 rpa_queue 表
        return {"status": "queued", "channel": "rpa"}
    
    # activation_count >= 3，标记休眠
    await db.execute("UPDATE users SET status='dormant' WHERE user_id=:uid", {"uid": user_id})
    return {"status": "failed", "reason": "user_dormant"}
```

### 调用方必须处理三态结果

```python
result = await send_proactive_message(user_id, reply)
if result["status"] == "sent":       # kf 即时成功
    await db.execute("UPDATE orders SET followup_sent=TRUE ...")
elif result["status"] == "queued":   # 进入 RPA 队列
    await db.execute("UPDATE orders SET followup_queued=TRUE ...")
elif result["status"] == "failed":   # 休眠用户
    await db.execute("UPDATE orders SET followup_failed=TRUE ...")
```

## 八、给凯撒的开发指引

### 你需要知道的核心规则

1. **所有消息发送必须走 `kf/send_msg`**，不要用 `message/send`（那是内部通讯用的）
2. **所有主动推送必须走 `send_proactive_message` 统一入口**，不要直接调 kf API
3. **定时任务中必须处理三态返回值**（sent/queued/failed），不能一律标记为"已发送"
4. **RPA 模块是独立组件**，运行在 Windows Server 上。**Phase 0-1：FastAPI 通过数据库任务队列（`rpa_queue` 表）调度 RPA**；Phase 2 以后视规模决定是否引入消息中间件（Redis Streams）

### 开发优先级

```
Phase 0（第1-2周）
  ├── ① FastAPI kf 回调网关（接收用户消息+事件）
  ├── ② kf/send_msg 发送模块（文字/链接/图片）
  ├── ③ enter_session 欢迎语触发
  └── ④ Spike：验证上述待验证事项

Phase 1（第3-4周）
  ├── ⑤ LangGraph 状态图对接 kf 通道
  ├── ⑥ send_proactive_message 统一推送入口
  └── ⑦ 定时任务调度引擎（APScheduler）

Phase 2（第5-6周）
  ├── ⑧ RPA 模块开发（客服工作台自动化）
  ├── ⑨ RPA 进程监控 + 告警
  └── ⑩ 沉默用户激活策略（D+1/D+4/D+10）
```
