## 三、🟡 中等问题

### 问题 1：SCRM 方案的成本和限制需要更具体

方案第 78-95 行提出"验证期用 SCRM（微盛/微伴）"，但只写了"月费 ¥几百-几千"和"受限于 SCRM 的开放程度"。

**需要补充：**
- 微盛和微伴是否支持接入自定义 AI API？（不是所有 SCRM 都有这个口子）
- 如果 SCRM 不支持自定义 AI 回复，那方案 A 的架构图就不成立
- 能否在 Phase 0 第 2-3 周做个实际评估，输出"SCRM 选型报告"？

**建议**：把第 134 行 SCRM 状态从"📋 待评估"改成"📋 Phase 0 第 2 周评估，输出选型报告"，给一个明确的时间点。

### 问题 2：方案 B（自建）需要"代开发"或 ISV 权限——这个卡点需要展开

第 113 行写"需申请代开发或 ISV 权限"，但没有展开。

**关键问题：**
- ISV 权限申请需要什么条件？需要营业执照以外的资质吗？
- 审核周期多长？
- 如果 ISV 申请不通过，方案 B 是否有其他路径？（比如"会话存档"接口的申请条件是什么？）

这个卡点如果被卡住，方案 B 的整个架构就实现不了——用户发消息后系统收不到。

**建议**：Phase 0 期间就开始调研 ISV/代开发的申请条件和周期，别等 Phase 1 结束后才发现需要半年审批。

### 问题 3：企微"每天每客户 1 条"群发限制的影响

第 71 行写"企业群发：每天每客户 1 条"——这意味着：

- 如果要推早安健康提醒 + 体质产品推荐 + 疗程提醒，**一天只能选一个发**
- 岐黄学社场景可能需要更高频的主动触达
- 1 条/天的限制下，推送内容的编排策略变得非常关键（今天发什么，不发什么）

**建议**：在方案中加一段"推送策略编排"——在一天一条的约束下，不同场景的优先级排序。例如：

```
优先级：疗程提醒 > 复购引导 > 节气养生 > 每日问候
当天已有高优先级推送时，低优先级延后
```

### 问题 4：Mem0 Spike 的验收标准需要更明确

第 261 行写"Phase 0 前 2 天做 Mem0 Spike（Docker + 20 条对话测试）"，但没有定义**什么算通过、什么算不通过**。

**建议**：Spike 验收标准定义——

| 验证项 | 通过标准 | 不通过则 |
|--------|---------|---------|
| Docker 部署 | 30 分钟内跑起来 | 排查→如果 2 小时搞不定就放弃 |
| 事实提取准确率 | ≥ 80%（20 条里正确提取 16+ 条） | 切 pgvector 自建方案 |
| 偏好提取准确率 | ≥ 70% | 可接受，后续优化 |
| 单次检索延迟 | < 500ms | 可接受到 1s，超过则排查 |
| 中文支持 | 能正确处理中文事实/偏好 | 不支持中文则直接放弃 |

## 四、💡 改进建议

### 建议 1：跟评审版技术方案对齐"AI 接入"描述

评审版技术方案（5/5）第 114 行写"AI 接入：腾讯 OpenClaw（微信官方通道）"，但本方案用的是企微 API + SCRM。

这两份文档如果同时给评委或合作方看，会产生困惑。**建议评审版同步更新微信接入的描述**，或在本方案中加一句注释说明与评审版的关系。

### 建议 2：Token 成本表补"对标岐黄 6 万用户"的数据

第 272-283 行只到 60000，但给的是"~¥20万"。精算模型里的数字是 ¥399,708（×2 保守值）。

两个数字不一致：
- 精算模型：60000 月活 → **~¥40 万/月**（保守 ×2）
- 本方案：60000 月活 → **~¥20 万**

看起来本方案用的是精算值而非 ×2 保守值。**建议标注清楚是精算值还是保守值**，避免内外口径不一致。

### 建议 3：加一个"第 3 周演示版"的具体 Demo 脚本

第 264 行定义了"🎯 3 周演示：扫码即可体验的 AI 健康管家"，这个里程碑非常好。

建议再补一个简短的演示流程脚本：

```
演示脚本（给岐黄/投资人看）：
1. 扫码加企微好友 → 自动收到欢迎语 + 体质测评卡片
2. 点卡片 → 进入 3 分钟体质测评
3. 测评完成 → AI 记住你的体质类型
4. 第二天来聊 → AI 主动说"昨天测出你是木型体质，今天推荐..."
5. 问具体问题 → AI 基于知识库回答
= "这就是 500 个客服做的事，现在一个 AI 做完了"
```
