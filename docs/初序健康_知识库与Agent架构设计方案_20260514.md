## 一、核心设计原则

### 1.1 业务价值优先
- **知识库不是技术炫技，是产品核心差异化价值**
- 初序健康的灵魂 = 五行体质理论 + 舌诊 + 个性化食谱
- 如果让 DeepSeek 自由发挥，就是"套壳 ChatGPT"，用户凭什么付费？

### 1.2 技术约束
- **零服务器成本**：只用 MemFire Cloud PostgreSQL + pgvector
- **零额外部署**：不引入 Milvus/Qdrant/ChromaDB 等独立服务
- **Serverless 优先**：所有服务都走 API 调用，不自建基础设施

### 1.3 MVP 聚焦
- **Phase 0 只做三件套**：舌诊知识库 + 食谱知识库 + 五行体质 System Prompt
- **不做过度设计**：不搞混合检索、不搞 Reranker、不搞复杂 Chunking
- **先跑通再优化**：用最简单的方案验证业务价值，再根据真实数据迭代

## 二、数据分析与结构设计

### 2.1 舌诊知识库分析

**原始数据特征：**
- 结构化程度高：舌体/舌色/舌苔三维度，每个维度有明确的特征→含义→体质映射
- 数据量小：约 30 条核心规则
- 查询模式：用户上传舌头照片 → 视觉识别 → 匹配规则 → 返回诊断

**表结构设计：`tongue_diagnosis`**

```sql
CREATE TABLE tongue_diagnosis (
    id SERIAL PRIMARY KEY,
    category VARCHAR(20) NOT NULL,  -- 'body'(舌体) / 'color'(舌色) / 'coating'(舌苔)
    feature VARCHAR(50) NOT NULL,   -- 特征描述，如"胖大有齿痕"
    meaning TEXT NOT NULL,          -- 含义解读，如"脾虚湿重，体内水分代谢差"
    related_constitution VARCHAR(20), -- 关联体质：wood/fire/earth/metal/water
    severity VARCHAR(20),           -- 严重程度：normal/mild/moderate/severe
    advice TEXT,                    -- 调理建议
    warning_flag BOOLEAN DEFAULT FALSE, -- 是否需要就医提醒
    embedding vector(1536),         -- 向量索引（用于语义检索）
    metadata JSONB,                 -- 扩展字段：{season_related, symptom_tags, etc.}
    created_at TIMESTAMP DEFAULT NOW()
);

-- 向量索引
CREATE INDEX ON tongue_diagnosis USING ivfflat (embedding vector_cosine_ops);

-- 复合索引（加速按体质+类别查询）
CREATE INDEX idx_tongue_constitution_category ON tongue_diagnosis(related_constitution, category);
```

**数据样例：**
```json

  }

```

### 2.2 食谱知识库分析

**原始数据特征：**
- 按五行体质分类：木/火/土/金/水
- 每个体质有：适宜食物、禁忌食物、饮食原则
- 数据量中等：约 100-150 条食材规则

**表结构设计：`food_knowledge`**

```sql
CREATE TABLE food_knowledge (
    id SERIAL PRIMARY KEY,
    food_name VARCHAR(100) NOT NULL,        -- 食物名称
    food_category VARCHAR(50),              -- 食物分类：蔬菜/水果/肉类/主食/茶饮
    constitution_type VARCHAR(20) NOT NULL, -- 适用体质：wood/fire/earth/metal/water/all
    suitability VARCHAR(20) NOT NULL,       -- 适宜度：recommended/neutral/avoid
    effect TEXT,                            -- 功效说明
    reason TEXT,                            -- 推荐/禁忌原因
    season VARCHAR(50),                     -- 适用季节：spring/summer/autumn/winter/all
    temperature VARCHAR(20),                -- 食物性质：hot/warm/neutral/cool/cold
    flavor VARCHAR(50),                     -- 五味：sour/bitter/sweet/spicy/salty
    embedding vector(1536),                 -- 向量索引
    metadata JSONB,                         -- 扩展字段：{cooking_method, pairing_suggestions, etc.}
    created_at TIMESTAMP DEFAULT NOW()
);

-- 向量索引
CREATE INDEX ON food_knowledge USING ivfflat (embedding vector_cosine_ops);

-- 复合索引（加速按体质+适宜度查询）
CREATE INDEX idx_food_constitution_suitability ON food_knowledge(constitution_type, suitability);

-- 季节索引
CREATE INDEX idx_food_season ON food_knowledge(season);
```

## 三、LangGraph 状态机设计

### 3.1 核心状态节点

```python
from typing import TypedDict, Literal

class AgentState(TypedDict):

    user_id: str
    user_name: str

    consecutive_days: int   # 连续打卡天数
    user_level: str         # 称号：养生新手/体质探索者/节律达人/养生大师
    
    # 对话上下文

    current_intent: str     # 当前意图：greeting/menu/food_recommend/tongue_diagnosis/check_in

graph.add_edge("intent_recognition", "food_recommend", condition=lambda s: s["current_intent"] == "food_recommend")
graph.add_edge("intent_recognition", "tongue_diagnosis", condition=lambda s: s["current_intent"] == "tongue_diagnosis")
# ... 其他边
```

### 3.2 知识库调用时机

**舌诊知识库调用：**
- 触发条件：用户上传图片 + 图片类型为"舌头"
- 调用流程：
  1. 视觉模型识别舌象特征（舌体/舌色/舌苔）
  2. 将特征描述向量化
  3. 在 `tongue_diagnosis` 表中检索 Top 3 匹配规则
  4. 结合用户已知体质（如果有）过滤结果
  5. 生成诊断报告

**食谱知识库调用：**
- 触发条件：用户选择"今天吃什么" 或 "拍照识食"
- 调用流程：
  1. 获取用户体质类型
  2. 获取当前节气、天气、时间段
  3. 在 `food_knowledge` 表中检索：
     - `constitution_type = 用户体质 AND suitability = 'recommended'`
     - `season = 当前节气 OR season = 'all'`
  4. 随机选择 3-5 个食材（避免重复昨天推荐）
  5. 生成推荐文案

**不调用知识库的场景：**
- 闲聊、打卡、查看报告 → 直接用 LLM 生成
- 体质测评 → 用 System Prompt 中的问卷逻辑

## 四、技术实现方案

### 4.1 向量化方案

**Embedding 模型选择：**
- **方案 A（推荐）**：DeepSeek API 的 Embedding 接口（如果有）
- **方案 B**：OpenAI `text-embedding-3-small`（1536 维，成本低）
- **方案 C**：本地模型 `bge-small-zh-v1.5`（512 维，需自建服务，不推荐）

**向量化流程：**
```python
import openai

def vectorize_text(text: str) -> list[float]:
    """将文本向量化"""
    response = openai.Embedding.create(
        model="text-embedding-3-small",
        input=text
    )
    return response['data'][0]['embedding']

# 舌诊数据向量化
feature_text = f"{category} {feature} {meaning}"
embedding = vectorize_text(feature_text)

# 食谱数据向量化
food_text = f"{food_name} {effect} {reason}"
embedding = vectorize_text(food_text)
```

### 4.2 检索方案

**简单向量检索（Phase 0）：**
```python
def search_tongue_diagnosis(query: str, constitution: str = None, top_k: int = 3):
    """舌诊知识检索"""
    query_embedding = vectorize_text(query)
    
    sql = """
    SELECT id, feature, meaning, advice, warning_flag,
           1 - (embedding <=> %s::vector) AS similarity
    FROM tongue_diagnosis
    WHERE (%s IS NULL OR related_constitution = %s)
    ORDER BY embedding <=> %s::vector
    LIMIT %s
    """
    
    results = db.execute(sql, (query_embedding, constitution, constitution, query_embedding, top_k))
    return results

def search_food_recommendations(constitution: str, season: str, exclude_ids: list = None, top_k: int = 5):
    """食谱推荐检索"""
    sql = """
    SELECT id, food_name, effect, reason, metadata
    FROM food_knowledge
    WHERE constitution_type IN (%s, 'all')
      AND suitability = 'recommended'
      AND (season = %s OR season = 'all')
      AND id NOT IN (%s)
    ORDER BY RANDOM()
    LIMIT %s
    """
    
    exclude_ids = exclude_ids or []
    results = db.execute(sql, (constitution, season, exclude_ids, top_k))
    return results
```

**为什么不用混合检索？**
1. 我们的数据已经高度结构化，Metadata 过滤足够精准
2. 用户查询已经在对话上下文中被 LLM 理解，不需要 BM25 抠字眼
3. 混合检索需要额外部署 Elasticsearch/Meilisearch，违反 Serverless 原则

### 4.3 LangGraph Tool 封装

```python
from langchain.tools import tool

@tool
def search_tongue_knowledge(tongue_features: str, user_constitution: str = None) -> str:
    """
    舌诊知识检索工具
    
    Args:
        tongue_features: 舌象特征描述，如"舌体胖大有齿痕，舌色淡白，舌苔白腻"
        user_constitution: 用户已知体质类型（可选）
    
    Returns:
        舌诊分析结果（JSON 字符串）
    """
    results = search_tongue_diagnosis(tongue_features, user_constitution)
    
    # 检查是否有就医提醒
    has_warning = any(r['warning_flag'] for r in results)
    
    return {
        "diagnosis": results,
        "warning": has_warning,
        "advice": [r['advice'] for r in results if r['advice']]
    }

@tool
def search_food_recommendations(user_constitution: str, current_season: str, history_food_ids: list = None) -> str:
    """
    食谱推荐工具
    
    Args:
        user_constitution: 用户体质类型
        current_season: 当前节气
        history_food_ids: 最近推荐过的食物 ID（避免重复）
    
    Returns:
        推荐食谱列表（JSON 字符串）
    """
    results = search_food_recommendations(user_constitution, current_season, history_food_ids)
    
    return {
        "recommended_foods": results,
        "match_score": random.randint(85, 98)  # 多变酬赏
    }

# 注册到 LangGraph
tools = [search_tongue_knowledge, search_food_recommendations]
```

```python
def load_tongue_diagnosis(json_file: str):
```

## 六、成本核算

### 6.1 向量化成本

**Embedding API 成本（OpenAI text-embedding-3-small）：**
- 价格：$0.02 / 1M tokens
- 舌诊数据：~30 条 × 50 tokens = 1,500 tokens ≈ $0.00003
- 食谱数据：~150 条 × 80 tokens = 12,000 tokens ≈ $0.00024
- **一次性成本：< $0.001**

### 6.2 检索成本

**pgvector 查询成本：**
- MemFire Cloud 免费额度：500MB 存储 + 1GB 传输
- 向量数据量：(30 + 150) × 1536 × 4 bytes ≈ 1.1 MB
- **存储成本：$0（在免费额度内）**

### 6.3 运行时成本

**每次对话的知识库调用：**
- 舌诊场景：1 次向量化（用户描述）+ 1 次检索 = ~100 tokens
- 食谱推荐：1 次检索（无需向量化，直接 SQL）= ~500 tokens 上下文
- **平均每次调用增加成本：~0.0001 元**

**20 轮/天对话中的知识库调用频次：**
- 舌诊：0.1 次/天（低频）
- 食谱推荐：1 次/天（高频）
- **日均知识库成本增幅：< 0.001 元/用户**

**结论：知识库对 Token 成本的影响可忽略不计（< 2%）**

## 八、验收标准

### 8.1 功能验收

**舌诊功能：**
- [ ] 用户上传舌头照片，能正确识别舌体/舌色/舌苔特征
- [ ] 返回的诊断结果与知识库匹配度 > 80%
- [ ] 严重异常情况能触发就医提醒

**食谱推荐功能：**
- [ ] 根据用户体质推荐食材，匹配度 > 90%
- [ ] 推荐结果考虑节气、天气因素
- [ ] 连续 3 天推荐不重复

**对话流程：**
- [ ] 首次用户能看到完整菜单
- [ ] 老用户能看到打卡天数和连续天数
- [ ] 所有回复符合提示词中的风格规范（简洁、口语化、有 emoji）

### 8.2 性能验收

- [ ] 知识库检索响应时间 < 500ms
- [ ] 单次对话 Token 消耗 < 2000 tokens
- [ ] 数据库查询 QPS > 100（压测）

### 8.3 合规验收

- [ ] 所有健康建议附带免责声明
- [ ] 不出现"诊断""治疗""药物"等医疗术语
- [ ] 严重异常情况必须建议就医

## 十、风险与应对

### 10.1 技术风险

**风险 1：pgvector 性能不足**
- 概率：低（数据量小，< 200 条）
- 影响：检索响应慢
- 应对：优化索引、增加缓存层

**风险 2：向量检索准确率低**
- 概率：中（取决于 Embedding 模型质量）
- 影响：推荐不准确
- 应对：先用 Metadata 过滤缩小范围，再用向量检索排序

### 10.2 业务风险

**风险 3：用户不信任 AI 健康建议**
- 概率：中
- 影响：留存率低
- 应对：强化免责声明、增加"真人营养师审核"标签（即使是 AI 生成）

**风险 4：知识库内容过时**
- 概率：高（中医理论更新慢，但食材流行趋势变化快）
- 影响：推荐不符合用户期待
- 应对：建立知识库更新机制，每季度 review 一次

## 十一、总结

### 核心设计思路
