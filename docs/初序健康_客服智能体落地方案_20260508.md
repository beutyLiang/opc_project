### 消息通道能力（v1.3 混合架构）

| 场景 | 通道 | 消息类型 | 限制 |
|------|------|---------|------|
| **用户发消息后 AI 自动回复** | kf/send_msg API | 文字+图片+链接+小程序卡片+语音+视频 | 48h 窗口内无限制 |
| **活跃用户主动推送**（<48h） | kf/send_msg API | 同上 | 48h 窗口内，全自动 |
| **沉默用户激活**（>48h） | RPA 客服工作台 | 文字 | D+1/D+4/D+10，最多3次 |

> [!IMPORTANT]
> **v1.3 关键规则**
>
> kf/send_msg 有 **48 小时会话窗口**限制：用户最后一次发消息后 48h 内有效。
> 窗口由**用户发消息**触发，企业发消息**不重置**窗口。
> 超过 48h 的沉默用户，API 返回 45015，通过 RPA 在客服工作台发激活消息。

### 消息收发架构（v1.3）

```
用户发消息 → 企微 kf 回调 → FastAPI 消息网关
                                  │
                                  ▼
                            LangGraph 状态机处理
                                  │
                                  ▼
                            kf/send_msg 回复 → 用户收到（全自动）

定时主动推送 → 调度引擎检查用户状态
                    │
              ┌─────┴─────┐
          活跃（<48h）   沉默（>48h）
              │               │
        kf/send_msg       RPA 激活队列
        全自动 ✅          D+1/D+4/D+10
                              │
                        用户回复 → AI 接管 ✅
```

- ✅ 不需要 SCRM（v1.3 已移除）
- ✅ 不需要 ISV/代开发资质
- ✅ AI 对话回复 + 活跃用户推送：全自动，开发即上线
- ✅ 沉默用户激活：RPA 低频操作，风险低

**决策（v1.3 最终版）**：采用**混合架构**——主通道为**微信客服（kf_account）**，辅助通道为 **RPA 沉默用户激活**。

| 用户状态 | 通道 | 方式 | 全自动？ |
|---------|------|------|:---:|
| 活跃用户（48h内有互动） | kf/send_msg API | AI 全自动回复 + 主动推送 | ✅ |
| 沉默用户（>48h未回复） | RPA 客服工作台 | 低频激活消息（D+1/D+4/D+10，最多3次） | ✅ |
| 用户回复 | kf/send_msg API | AI 立刻接管，恢复全自动 | ✅ |
| 休眠用户（3次激活未回复） | 停止推送 | 标记休眠，等待用户主动回来 | — |

> **关键规则**：kf/send_msg 有 48 小时会话窗口限制——用户最后一次发消息后 48 小时内有效。窗口由**用户发消息**触发，企业发消息不重置窗口。

## 三、技术选型定稿

### 核心决策表

| 决策项 | 选定方案 | 备选 | 决策依据 | 状态 |
|--------|---------|------|---------|:----:|
| 微信通道 | **企微·微信客服（kf_account）+ RPA 激活** | 企微外部联系人 | kf 原生全自动（活跃用户）+ RPA 低频激活（沉默用户）；外部联系人群发必须员工确认，不可用 | ✅ 已定 |
| Agent 框架 | **LangGraph** | Dify / 传统 LangChain | 五大需求中3个需深度自定义代码，状态机架构可完美解决打断与流程回退 | ✅ 已定 |
| LLM 模型 | **DeepSeek V4 Flash** | Qwen-Max | 全国产、数据不出境、成本最优 | ✅ 已定 |
| 记忆系统 | **Mem0** | 自建 pgvector | 轻量快速、Docker 部署、社区活跃 | ⏳ 待 Spike |
| 知识库 | **RAG（自建）** | Dify 知识库 | LangGraph 生态原生支持 RAG 节点，无需额外平台 | ✅ 已定 |
| 向量数据库 | **pgvector (MemFire Cloud)** | Milvus | 已有 MemFire，PostgreSQL 原生支持 | ✅ 已定 |
| 数据库 | **MemFire Cloud (PostgreSQL)** | — | 国产、支持 pgvector + RLS | ✅ 已定 |
| 消息网关 | **自建 (FastAPI)** | — | 处理企微kf回调/路由/推送调度 | 📋 待开发 |
| SCRM | **不需要** | — | kf_account 通道原生支持 AI 全自动收发，无需 SCRM 中间层 | ✅ 简化 |

### 为什么选 LangGraph 而不是 Dify 或传统 LangChain？

| 维度 | Dify / 传统 LangChain | LangGraph 状态机架构 |
|------|------|-----------|
| 知识库管理 | ⭐⭐⭐⭐⭐ 可视化 | ⭐⭐⭐ 需自建 |
| 主动推送调度 | ❌ 做不了 | ✅ 代码完全可控 |
| OPC 渠道归属 | ⭐⭐ HTTP 节点受限 | ✅ 直接调用数据库 |
| 记忆系统集成 | 需外接 | ✅ 原生 Memory 生态 |
| 企微消息网关 | 需自建 | 同样需自建 |
| 长期可控性 | Dify 受限 / LangChain 存在黑盒 | **基于图结构的完全可控** |

> **核心逻辑**：不管用哪个框架，企微消息网关和推送调度都得自建。既然 70% 的代码都要自己写，不如 100% 自己掌控。

## 六、人机协同与人工介入

### 核心原则

> AI 处理 80% 的日常咨询，但"最后一公里"由真人完成。用户**无需切换应用或对话框**，在同一个聊天窗口里，对面从 AI 无感切换为真人。

### 三种服务模式

| 模式 | 用户感知 | 适用场景 | 实现方式 |
|------|---------|---------|---------|
| **AI 全自动** | 秒回，7×24 | 日常咨询、产品推荐、养生问答 | 消息 → 网关 → LangGraph 状态图 → 自动回复 |
| **真人接管** | 可能稍慢，工作时间 | 退款、投诉、专业医疗、大单促成 | 消息 → 网关判断 → 不送 Agent → 真人在企微 App 直接回复 |
| **协同模式** | 速度适中 | AI 不太确定时 | 消息 → Agent 起草建议 → 真人审核修改 → 发出 |

### 为什么能做到"无感切换"？

用户聊天的对象是**"初序·小安"这个企微账号**，而非某个 AI 或某个人。企微外部联系人模式下，多个员工可以操作同一个账号：

- AI 回复时：消息通过 API 以"小安"的名义发出
- 真人回复时：真人在企微 App 里以"小安"的名义手动发出
- **用户看到的始终是"初序·小安"在跟自己聊天**

### 技术实现

数据库 `users` 表增加 `service_mode` 字段：

| 字段值 | 含义 | 消息网关行为 |
|-------|------|------------|
| `ai` | AI 全自动（默认） | 消息送 Agent，自动回复 |
| `human` | 真人接管 | 消息**不送** Agent，通知真人处理 |
| `copilot` | 协同模式 | Agent 生成草稿 → 推送给真人审核 → 真人确认后发出 |

### 触发条件

| 触发方式 | 场景 | 实现 |
|---------|------|------|
| AI 主动转交 | AI 识别到答不了（退款、投诉、专业医疗） | Agent 判断 → `service_mode='human'` → 通知真人 |
| 用户要求 | 用户说"找真人""转人工" | Agent 意图识别 → 同上 |
| 运营主动介入 | 后台发现高价值用户/敏感对话 | 运营后台操作 → 改 `service_mode` |
| 自动回切 | 真人处理完毕，点击"转回AI" | 运营后台操作 → `service_mode='ai'` |

### 通知机制

真人被通知接管时，通过**企微内部消息/钉钉/飞书**推送提醒，包含：
- 用户昵称和体质标签
- 最近 5 条对话摘要（Agent 自动总结）
- AI 判断转交的原因

## 十二、核心结论

> [!TIP]
> **五个需求全部可落地。** 关键路径：
> 1. **企微用「微信客服 kf_account」模式**——原生支持 AI 全自动回复和主动推送，无需 SCRM、无需 ISV

## 附录B：RPA 沉默用户激活方案（v1.3 正式纳入架构）

> [!NOTE]
> **此方案已作为 v1.3 混合架构的正式组成部分**，专门解决 kf_account 48 小时窗口过期后的沉默用户触达问题。RPA 仅用于低频激活，不用于大规模群发。

### 方案定位

| 对比项 | 旧方案（v1.0 RPA 全量群发） | 新方案（v1.3 RPA 激活） |
|--------|:---:|:---:|
| 目标 | 替代所有推送 | 仅激活沉默用户 |
| 频率 | 每天对所有用户 | 最多3次/用户，间隔递增 |
| 风险 | 🔴 高 | 🟢 低（与真人客服行为一致） |
| 地位 | 备选方案 | **正式架构组件** |

### 激活频率衰减策略

```
用户沉默 > 48h
    │
    ├── D+1（沉默第1天）：发激活消息 #1
    │     "小安这边关心一下你，这几天感觉怎么样呀？"
    │
    ├── D+4（沉默第4天）：发激活消息 #2
    │     "好久没聊了，最近有没有按时吃药呢？"
    │
    ├── D+10（沉默第10天）：发激活消息 #3（最后一次）
    │     "小安一直在这里，有需要随时找我哦~"
    │
    └── D+10 后：停止推送，标记为「休眠用户」

任何时刻用户回复 → 48h 窗口重置 → AI 立刻全自动接管
```

### 技术实现

**架构图：**
```
FastAPI 调度引擎（检测沉默用户）
         │
    沉默 > 48h？ ── 否 → kf/send_msg 正常推送
         │
        是
         │
    判断激活次数 ── ≥3次 → 标记休眠，停止
         │
        <3次
         │
    RPA 通过客服工作台网页发消息
         │
    消息到达用户（客服窗口） ✅
         │
    用户回复 → 窗口重置 → AI 接管
```

**核心代码（Python）：**
```python
import uiautomation as auto
import time
from datetime import datetime, timedelta

ACTIVATION_SCHEDULE = [1, 4, 10]  # 沉默后第1、4、10天发激活消息

class SilentUserActivator:
    def should_activate(self, user) -> bool:
        """判断是否需要发激活消息"""
        silent_days = (datetime.now() - user.last_message_at).days
        return (
            silent_days in ACTIVATION_SCHEDULE
            and user.activation_count < 3
            and user.status != "dormant"
        )
    
    def send_activation(self, user):
        """通过客服工作台 UI 发激活消息"""
        messages = [
            "小安这边关心一下你，这几天感觉怎么样呀？",
            "好久没聊了，最近有没有按时吃药呢？",
            "小安一直在这里，有需要随时找我哦~"
        ]
        msg = messages[user.activation_count]
        
        # RPA 在客服工作台发送
        self._rpa_send_via_kf_console(user.kf_session_id, msg)
        
        # 更新激活计数
        user.activation_count += 1
        if user.activation_count >= 3:
            user.status = "dormant"  # 标记休眠
```
