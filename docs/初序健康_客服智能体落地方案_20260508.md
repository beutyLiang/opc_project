### 三层消息能力

| 场景 | API 接口 | 消息类型 | 限制 |
|------|---------|---------|------|
| **加好友瞬间** | `send_welcome_msg` | 文字+图片+链接+小程序卡片 | 仅一次机会 |
| **日常主动推送** | `add_msg_template`（企业群发） | 文字+图片+链接+小程序卡片 | 每天每客户 1 条 |
| **用户发消息后自动回复** | 需 SCRM 或自建方案 | 全类型 | 见下方详解 |

### 自动回复的实现方案

用户日常发消息过来，AI 自动回复——这是核心能力，有两条路：

**方案 A：接入第三方 SCRM（推荐先用这个验证）**

```
用户发消息 → 企微 → SCRM系统（微盛/微伴）拦截
                          │
                          ▼
                    调用我们的 AI API
                    (LangChain Agent)
                          │
                          ▼
                    SCRM 代发回复 → 用户收到
```

- ✅ 成熟方案，市面大量企业在用
- ✅ 不需要自己处理企微消息加解密
- ⚠️ 月费 ¥几百-几千
- ⚠️ 受限于 SCRM 的开放程度

**方案 B：自建系统（长期方案）**

```
用户发消息 → 企微 → 会话存档 SDK 拉取
                          │
                          ▼
                    自建消息网关 (FastAPI)
                          │
                          ▼
                    LangChain Agent 处理
                          │
                          ▼
                    企微 API 回复 → 用户收到
```

- ✅ 完全自主可控
- ✅ 无第三方依赖
- ⚠️ 需申请「代开发」或 ISV 权限
- ⚠️ 开发周期较长

**建议**：验证期用方案 A 快速跑通，同步开发方案 B。

## 三、技术选型定稿

### 核心决策表

| 决策项 | 选定方案 | 备选 | 决策依据 | 状态 |
|--------|---------|------|---------|:----:|
| 微信通道 | **企微·外部联系人** | 微信客服 | 实证：在聊天列表显示如好友，信任感强 | ✅ 已定 |
| Agent 框架 | **LangChain** | Dify | 五大需求中3个需深度自定义代码，LangChain 灵活度最高 | ✅ 已定 |
| LLM 模型 | **DeepSeek V4 Flash** | Qwen-Max | 全国产、数据不出境、成本最优 | ✅ 已定 |
| 记忆系统 | **Mem0** | 自建 pgvector | 轻量快速、Docker 部署、社区活跃 | ⏳ 待 Spike |
| 知识库 | **RAG（自建）** | Dify 知识库 | LangChain 原生支持 RAG，无需额外平台 | ✅ 已定 |
| 向量数据库 | **pgvector (MemFire Cloud)** | Milvus | 已有 MemFire，PostgreSQL 原生支持 | ✅ 已定 |
| 数据库 | **MemFire Cloud (PostgreSQL)** | — | 国产、支持 pgvector + RLS | ✅ 已定 |
| 消息网关 | **自建 (FastAPI)** | — | 处理企微回调/加解密/路由/推送调度 | 📋 待开发 |
| SCRM（过渡） | **微盛 或 微伴** | — | 快速实现自动回复，验证期使用 | 📋 待评估 |

### 为什么选 LangChain 而不是 Dify？

| 维度 | Dify | LangChain |
|------|------|-----------|
| 知识库管理 | ⭐⭐⭐⭐⭐ 可视化 | ⭐⭐⭐ 需自建 |
| 主动推送调度 | ❌ 做不了 | ✅ 代码完全可控 |
| OPC 渠道归属 | ⭐⭐ HTTP 节点受限 | ✅ 直接调用数据库 |
| 记忆系统集成 | 需外接 | ✅ 原生 Memory 生态 |
| 企微消息网关 | 需自建 | 同样需自建 |
| 长期可控性 | 受 Dify 版本限制 | **完全自主** |

> **核心逻辑**：不管用哪个框架，企微消息网关和推送调度都得自建。既然 70% 的代码都要自己写，不如 100% 自己掌控。

## 五、智能体可调用的后端 API

| 调用场景 | 接口示例 | 触发时机 |
|---------|---------|----------|
| 用户来源归属 | `POST /api/user/bindOPC` | 用户首次添加企微时（活码 state 参数） |
| 查询用户画像 | `GET /api/user/profile` | 对话中需要个性化回复时 |
| 自动打标签 | `POST /api/user/tag` | 测评完成后自动分类 |
| 查询产品库存 | `GET /api/product/stock` | 推荐产品前检查有无货 |
| 创建订单 | `POST /api/order/create` | 用户确认购买时 |
| 查看佣金/分成 | `GET /api/opc/commission` | OPC 查看自己的业绩时 |
| 疗程进度更新 | `POST /api/treatment/update` | 售后关怀/复购提醒时 |
| 数据看板统计 | `GET /api/stats/opc/{id}` | OPC 管理员查看运营数据时 |

### 渠道追踪：企微渠道活码

```
OPC-A 专属活码 → 用户扫码 → 回调 state="OPC-A" → 自动绑定 → 数据库
OPC-B 专属活码 → 用户扫码 → 回调 state="OPC-B" → 自动绑定 → 数据库
```

### 数据隔离：PostgreSQL RLS

每个 OPC 只能看到自己的用户/订单/对话数据，通过 PostgreSQL 原生行级安全策略实现，MemFire Cloud 直接支持。

## 七、记忆系统

### 分阶段演进

| 阶段 | 方案 | 说明 |
|------|------|------|
| 验证期（0-3月） | Mem0 + PostgreSQL | 验证记忆提取准确率和延迟 |

| 规模期（7-12月） | 迁移至 Zep 或完全自建 | 支持复杂时序推理 |

### 记住什么

- 用户体质类型、偏好食材、过敏信息

- 情绪状态、沟通风格偏好
- 家庭成员健康情况
- 重要日期（生日、疗程开始日等）

## 十一、核心结论

> [!TIP]
> **五个需求全部可落地。** 关键路径：
> 1. **企微用「外部联系人」模式**——像真人好友出现在聊天列表（已通过特步实证）
> 2. **Agent 用 LangChain 全栈自建**——五大需求中3个需深度定制，全链路自主可控
> 3. **自动回复过渡期用 SCRM**——快速跑通，同步自建长期方案
> 4. **Mem0 做 Spike 验证**——2 天确认记忆系统可用性
> 5. **企微注册和开发双线并行**——第 3 周出可演示版本，不空等营业执照
> 6. **渠道活码 + RLS 实现 OPC 数据隔离**——从扫码那一刻起自动追踪归属

**落地时间**：双线并行约 **8-10 周** 跑通全链路 MVP。**第 3 周即可出可扫码体验的演示版本。**

> [!NOTE]
> 本方案为通用智能体架构方案。针对岐黄学社的具体接入（现有群迁移、部署模式、合作协议等），需另出 **《岐黄学社 AI 客服改造专项方案》**。
