## 1. 业务需求场景映射

初序健康的 Agent 不是一个简单的"问答机器人（QA Bot）"，而是一个**数字医疗健康管家**，它具有以下严苛要求：
- **强状态依赖（Stateful）**：需要精准记录用户当前处于"首诊收集阶段"、"等待体检报告阶段"还是"48小时沉默唤醒阶段"。
- **非线性对话（Cyclic Logic）**：诊断过程中用户经常跑题、反问，Agent 需要在打断后重新回到"核心问诊流（State Flow）"。
- **高确定性与容错（Determinism）**：开方和健康建议不能有任何不可控的"幻觉行为"，每个节点的 Prompt 和调用都要精确可查。
- **人工介入（Human-in-the-loop）**：退款、投诉、专业医疗等场景需无感切换至真人。

## 2. 业界主流 Agent 框架对比 (2024 - 2026)

### 方案 A：传统 LangChain AgentExecutor（原定方案）
- **核心机制**：基于 Chain 和 AgentExecutor，通过高度封装的 Pipeline 运行。
- **优点**：
  - 生态最庞大，开箱即用的 Tools（比如发微信、查数据库、搜索）极多。
  - MVP（最小可行性产品）开发速度最快。
- **致命缺陷**：
  - **过度封装（黑盒效应）**：当遇到意料之外的报错时（例如模型格式化输出失败），调试成本极高。
  - **线性思维**：对于长周期对话，无法精细化控制状态流转，很难实现复杂的条件判断和回退机制。
- **定位（重要澄清）**：
  - ❌ 不是"废弃 LangChain"——LangChain 的底层组件（`ChatModel`、`Retriever`、`Tool` 定义、`Document Loader` 等）**仍然继续使用**。
  - ✅ 废弃的是 `AgentExecutor` 这个线性编排器，用 LangGraph 的图结构编排替代它。

### 方案 B：LangGraph（官方进阶编排层 · **【最终选定】**）
- **核心机制**：在 LangChain 组件层之上引入 **状态机（State Machine）** 和 **图结构（Graph）** 作为编排层。
- **与 LangChain 的关系**：

  ```
  ┌─────────────────────────────────────────┐
  │           LangGraph（编排层）              │
  │  • 定义节点（Nodes）和边（Edges）          │
  │  • 管理状态流转、条件分支、循环            │
  │  • Checkpointer 持久化状态                │
  │  • Human-in-the-loop 原生支持             │
  └──────────────────┬────────────────────────┘
                     │ 调用
  ┌──────────────────┴────────────────────────┐
  │         LangChain（组件层）                 │
  │  • ChatModel：封装 DeepSeek API 调用       │
  │  • Retriever：RAG 知识库检索（pgvector）    │
  │  • Tools：产品查询、标签更新、订单创建等     │
  │  • Document Loader：知识库文档切分与索引     │
  └─────────────────────────────────────────────┘
  ```

- **优点**：
  - **完美契合医疗问诊**：你可以把问诊流定义为一个图（Graph），比如：闲聊节点 → 问诊节点 → 查知识库节点 → 给出建议节点。
  - **支持循环和打断**：用户偏题后，Graph 的状态依然保存在上下文中，随时可以继续。
  - **原生支持 Human-in-the-loop**：可以直接满足我们架构里"人工客服介入并修改回复"的需求。
  - **Checkpointer 持久化**：状态可以持久化到数据库（我们使用 MemFire PostgreSQL），实现跨会话的状态恢复。
  - **子图（Subgraph）**：可以将问诊、推荐、售后等模块封装为独立子图，解耦维护。
  - **时间旅行（Time Travel）**：可以回溯任意历史状态节点，用于对话质检和问题定位。
- **缺点**：
  - 学习曲线较为陡峭，开发团队需要适应节点（Nodes）和边（Edges）的声明式编程。
- **适用建议**：**最契合初序业务特点的中长期首选方案。**

### 方案 C：原生代码驱动（Pure Python / FastAPI）
- **核心机制**：完全抛弃上层封装，直接调用 DeepSeek / OpenAI 的原生 SDK，用纯粹的 Python `if/else`, `while` 循环和数据库表来控制所有的状态。
- **优点**：
  - **绝对的控制力**：没有黑盒，所有的逻辑都在明面上，性能最快，没有任何冗余依赖。
- **缺点**：
  - 需要自己造很多轮子（比如多并发下的记忆管理、重试逻辑、状态持久化等）。
  - **对团队要求极高**：xAI 等一线大厂用此路线，是因为拥有顶尖工程团队。对于初序目前的小团队规模（1-2 名核心开发），自建状态机、检查点、回溯能力的工程量远大于直接使用 LangGraph。
- **适用建议**：**作为 Plan B 保留**——如果 LangGraph 在实际开发中遇到不可解决的限制，可以切换至此方案。但当前阶段不推荐作为首选。

### 方案 D：多智能体协作框架（AutoGen / CrewAI）
- **核心机制**：让多个 Persona 的 Agent 互相交谈合作（例如：一个门诊医生 Agent + 一个药师 Agent + 一个质检 Agent）。
- **缺点与建议**：目前初序第一阶段的核心痛点在于"单点用户的深度沟通闭环"，采用多 Agent 框架会导致系统复杂度几何级数上升，暂时**不推荐**。

## 3. LangGraph 如何嵌入现有 v1.4 架构

> [!IMPORTANT]
> 这是凯撒最需要理解的部分——LangGraph 不是一个独立系统，而是嵌入到已有的 kf_account + FastAPI + Mem0 架构中的"大脑升级"。

### 架构嵌入示意图

```
用户发消息 → 企微 kf 回调 → FastAPI 消息网关
                                  │
                           检查 service_mode
                                  │
                   ┌──────────────┼──────────────┐
                   │              │              │
                  ai           human         copilot
                   │              │              │
                   ▼              ▼              ▼
            LangGraph 状态图    仅存档      Agent草稿→审核
                   │
         ┌─────────┼─────────┐
         │         │         │
    闲聊节点   问诊节点   推荐节点    ← LangGraph Nodes
         │         │         │
         │    ┌────┴────┐    │
         │    │         │    │
         ▼    ▼         ▼    ▼
     LangChain 组件层（共享）
     • ChatModel → DeepSeek API
     • Retriever → pgvector RAG
     • Tools → 产品/订单/标签 API
     • Mem0 → 长期记忆读写
                   │
                   ▼
          kf/send_msg → 用户收到回复
```

### 关键技术映射

| 现有架构组件 | LangGraph 对接方式 | 说明 |
|-------------|-------------------|------|
| FastAPI 消息网关 | 网关调用 `graph.ainvoke(state)` | 网关不变，仅替换原来调用 AgentExecutor 的入口 |
| Mem0 记忆系统 | 作为 Graph 节点的输入/输出 | 节点开始时 `mem0.search()`，结束时 `mem0.add()` |
| DeepSeek V4 Flash | 通过 LangChain ChatModel 封装调用 | LangGraph 节点内部使用 LangChain 的 LLM 组件 |
| pgvector RAG | 通过 LangChain Retriever 封装检索 | 作为独立的 RAG 检索节点 |
| MemFire PostgreSQL | **Checkpointer 持久化存储** | LangGraph 的 `PostgresSaver` 直接对接 MemFire |
| Tool Calling | LangChain `@tool` 定义不变 | 产品查询/订单创建/标签更新等工具定义不变 |
| RPA 沉默激活 | 不涉及 LangGraph | RPA 模块独立运行，通过 `rpa_queue` 表调度 |

### 子图规划（模块化设计）

| 子图 | 职责 | 典型节点 |
|------|------|---------|
| `chat_subgraph` | 日常闲聊、养生问答 | 意图识别 → RAG 检索 → 回复生成 |
| `consult_subgraph` | 问诊收集、体质分析 | 症状收集 → 体质判断 → 建议生成 |
| `recommend_subgraph` | 产品推荐、下单引导 | 库存查询 → 匹配推荐 → 发送卡片 |
| `aftercare_subgraph` | 售后关怀、复购提醒 | 疗程进度检查 → 效果回访 → 复购引导 |
| `escalation_subgraph` | 人工转交 | 转交判断 → 通知真人 → 上下文摘要 |

## 4. 迁移影响评估

> [!WARNING]
> 已通过审核的《技术实现说明书》中的伪代码需要逐步重写为 LangGraph 节点写法。以下是影响范围评估。

### 需要重写的部分

| 原代码模块 | 变化内容 | 工作量评估 |
|-----------|---------|:---------:|
| `call_langgraph_agent()` | 从函数式改为 Graph 节点声明式 | 🟡 中 |
| `handle_ai_reply()` | 从直接调用 Agent 改为 `graph.ainvoke()` | 🟢 低 |
| `send_quiz_result_analysis()` | 封装为问诊子图的终止节点 | 🟡 中 |
| `recommend_product()` Tool 定义 | Tool 本身不变，注册方式从 AgentExecutor 改为 Graph Node | 🟢 低 |

### 不需要改动的部分

| 模块 | 原因 |
|------|------|
| FastAPI 消息网关（回调/路由/加解密） | 与 Agent 框架无关 |
| `send_text_to_user()` / kf API 封装 | 纯 HTTP 调用，与框架无关 |
| Mem0 记忆系统接口 | 只是被 Graph 节点调用，接口本身不变 |
| RPA 沉默用户激活模块 | 独立组件，不涉及 Agent 框架 |
| 数据库 Schema（users/chat_history 等） | 仅新增 `checkpoints` 表存储 LangGraph 状态 |

### 新增开发项

| 新增项 | 说明 | 阶段 |
|-------|------|------|
| `checkpoints` 表 | LangGraph Checkpointer 持久化，存储在 MemFire PostgreSQL | Phase 0 |
| Graph 定义文件 | 定义节点、边、条件分支的核心文件 | Phase 0 |
| 子图拆分 | 将单体 Graph 拆分为问诊/推荐/售后子图 | Phase 2 |

## 5. 最终推进建议

为了兼顾**开发速度**与**系统可控性**，建议如下：

1. **底层设施层**：继续使用 FastAPI 作为网关，衔接微信 `kf/send_msg` 和 RPA 触发器。**无需改动。**
2. **组件层**：继续使用 LangChain 的 `ChatModel`、`Retriever`、`Tool` 等组件封装。**无需改动。**
3. **编排层（核心变化）**：废弃传统 `AgentExecutor` 线性调度，引入 **LangGraph** 状态机作为编排层。
4. **持久化层**：新增 `checkpoints` 表，使用 LangGraph 官方的 `PostgresSaver` 对接 MemFire Cloud。
5. **下一步行动（Call to Action）**：
   - 建议凯撒与技术合伙人深度沟通，确认团队对 LangGraph 节点/边声明式编程的掌握程度。
   - Phase 0 第一周：先跑通一个最小 Graph（接收消息 → 查记忆 → 调 LLM → 回复），验证整个链路。
   - 如果团队觉得 LangGraph 学习成本过高，则采用 **方案 C（纯 Python 原生控制）** 作为 Plan B。

## 附录：关键术语对照

| 术语 | 含义 |
|------|------|
| Node（节点） | Graph 中的一个处理单元，如"检索记忆"、"调用 LLM"、"查产品库" |
| Edge（边） | 节点之间的连接，定义流转方向 |
| Conditional Edge（条件边） | 根据状态判断走哪条路（如：service_mode == human → 转交真人） |
| State（状态） | 整个 Graph 运行时的上下文数据，包含用户消息、记忆、中间结果等 |
| Checkpointer | 将 State 持久化到数据库，支持跨会话恢复和时间旅行 |
| Subgraph（子图） | 可独立编译的子 Graph，用于模块化（问诊子图、推荐子图等） |
| Human-in-the-loop | 在 Graph 运行中暂停，等待人工审核后继续 |
