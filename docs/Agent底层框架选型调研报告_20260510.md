# 初序健康 · Agent 底层框架选型调研报告 (2026版)

**撰写人**：子默
**日期**：2026年05月10日
**目标读者**：凯撒及技术研发团队
**背景**：在“初序健康”项目消息架构定稿（kf_account + RPA 辅助）后，系统需要一个强大的核心大脑（Agent）来处理长周期的医疗问诊、状态记忆与多步决策流。传统 LangChain 在应对高度结构化、存在复杂分支逻辑的对话场景时暴露出了严重的“黑盒化”与“状态失控”风险，特此出具最新的业界选型与建议。

---

## 1. 业务需求场景映射

初序健康的 Agent 不是一个简单的“问答机器人（QA Bot）”，而是一个**数字医疗健康管家**，它具有以下严苛要求：
- **强状态依赖（Stateful）**：需要精准记录用户当前处于“首诊收集阶段”、“等待体检报告阶段”还是“48小时沉默唤醒阶段”。
- **非线性对话（Cyclic Logic）**：诊断过程中用户经常跑题、反问，Agent 需要在打断后重新回到“核心问诊流（State Flow）”。
- **高确定性与容错（Determinism）**：开方和健康建议不能有任何不可控的“幻觉行为”，每个节点的 Prompt 和调用都要精确可查。

---

## 2. 业界主流 Agent 框架对比 (2024 - 2026)

### 方案 A：传统 LangChain (目前原定方案)
- **核心机制**：基于 Chain 和 AgentExecutor，通过高度封装的 Pipeline 运行。
- **优点**：
  - 生态最庞大，开箱即用的 Tools（比如发微信、查数据库、搜索）极多。
  - MVP（最小可行性产品）开发速度最快。
- **致命缺陷**：
  - **过度封装（黑盒效应）**：当遇到意料之外的报错时（例如模型格式化输出失败），调试成本极高。
  - **线性思维**：对于长周期对话，无法精细化控制状态流转，很难实现复杂的条件判断和回退机制。
- **适用建议**：**不建议作为核心架构，降级为底层工具库使用**（仅调用其文档切分、基础 LLM 封装模块）。

### 方案 B：LangGraph (官方进阶方案 · 【强烈推荐】)
- **核心机制**：引入了 **状态机（State Machine）** 和 **图结构（Graph）** 的概念。
- **优点**：
  - **完美契合医疗问诊**：你可以把问诊流定义为一个图（Graph），比如：闲聊节点 -> 问诊节点 -> 查知识库节点 -> 给出建议节点。
  - **支持循环和打断**：用户偏题后，Graph 的状态依然保存在上下文中，随时可以继续。
  - **原生支持 Human-in-the-loop**：可以直接满足我们架构里“人工客服介入并修改回复”的需求。
- **缺点**：
  - 学习曲线较为陡峭，开发团队需要适应节点（Nodes）和边（Edges）的声明式编程。
- **适用建议**：**最契合初序业务特点的中长期首选方案。**

### 方案 C：原生代码驱动 (Pure Python / FastAPI)
- **核心机制**：完全抛弃沉重的上层封装，直接调用 DeepSeek / OpenAI 的原生 SDK，用纯粹的 Python `if/else`, `while` 循环和数据库表来控制所有的状态。
- **优点**：
  - **绝对的控制力**：没有黑盒，所有的逻辑都在明面上，性能最快，没有任何冗余依赖。
  - **业界顶级大厂标配**：xAI 等一线团队首选路线。
- **缺点**：
  - 需要自己造很多轮子（比如多并发下的记忆管理、重试逻辑等）。
- **适用建议**：**如果凯撒的技术团队（或者外包大牛）具有非常深厚的工程功底，这是最稳健、没有任何后期包袱的路线。**

### 方案 D：多智能体协作框架 (AutoGen / CrewAI)
- **核心机制**：让多个 Persona 的 Agent 互相交谈合作（例如：一个门诊医生 Agent + 一个药师 Agent + 一个质检 Agent）。
- **缺点与建议**：目前初序第一阶段的核心痛点在于“单点用户的深度沟通闭环”，采用多 Agent 框架会导致系统复杂度几何级数上升，暂时**不推荐**。

---

## 3. 最终推进建议

为了兼顾**开发速度**与**系统可控性**，我建议：

1. **底层设施层**：继续使用 FastAPI 作为网关，衔接微信 `kf/send_msg` 和 RPA 触发器。
2. **状态控制层（核心变化）**：将核心的逻辑编排从传统 LangChain 替换为 **LangGraph**。
3. **下一步行动（Call to Action）**：
   - 建议凯撒与技术合伙人深度沟通，确认团队对 LangGraph 的掌握程度。
   - 如果团队觉得 LangGraph 学习成本过高，则直接建议采用 **方案 C（纯 Python 原生控制）**，因为长线来看，手写状态机的稳定性远大于用传统 LangChain 打满补丁的脆弱系统。
